# Task 03 报告：原子收货确认与 FIFO 出库确认

日期：2026-08-09

分支：`codex/warehouse-forward-port`

范围：第二版 ERP 的仓库收货确认、FIFO 出库确认、批次成本冻结、确认幂等与并发安全。未包含 Task 4 项目成本过账、退库确认、页面、部署或线上数据操作。

## 结果

仓库负责人现在可以通过两个严格 RPC 确认待处理单据：采购收货确认会原子创建一个收货批次、货架余额和入库流水；出库确认会按 `received_at, batch_id` 的稳定顺序消耗 FIFO 批次，并为每个实际消耗批次追加一条不可变出库流水。任意校验、权限、成本或库存不足都会回滚整笔确认，不会留下半张已确认单、部分库存或部分流水。

浏览器只提交单据 ID、行 ID、确认数量、来源仓库/货架和确认幂等键。确认人、确认时间、采购成本和最终流水均由数据库权威生成；服务层拒绝客户端传入价格、操作人、确认时间或额外字段。

## 收货、成本与批次边界

- 采购单 `totalCost` 必须是非负 JSON 数字，采购数量必须有效；单位成本由数据库按 `round(totalCost / orderedQuantity, 4)` 计算。
- 确认数量、采购单位成本和出库冻结总成本与浏览器 `Number` 可无损表达的十进制上限一致：三位数量最高 `9007199254740.990`，四位成本最高 `900719925474.0991`；超过一个最小单位即在任何库存写入前拒绝。
- 即使数据库里已有旧的超上限 `pending` 行，确认也会失败关闭；不会因为历史宽范围数据导致数据库已提交而客户端报 502。
- 收货确认锁顺序为：收货单、采购行 `FOR UPDATE`、采购记录 advisory lock、仓库/货架升序、型号升序；与采购提交和修改使用同一序列化边界。
- 一个收货行最多生成一个批次；批次 `(receipt_line_id, variant_id)` 必须对应真实收货行，防止伪造或串型号。
- 批次成本和流水成本在确认时冻结；后续采购总价或型号参考价变化不会改写历史出库成本。
- `warehouse.receipt.confirm` 与 `warehouse.cost.view` 独立。没有成本查看权限的确认响应把 `unitCost` 返回为 `null`，但数据库仍保存权威成本。

## FIFO 出库与失败关闭

- 出库确认请求必须逐行绑定准确的来源仓库和货架；响应也返回权威来源仓库/货架，客户端不能把另一来源的结果当成当前请求。
- 数据库先锁仓库/货架和型号资源，再按 FIFO 顺序锁候选批次余额。跨多个批次时逐批记录流水并累计冻结成本。
- 选定来源库存不足时整笔回滚：申请单保持 `pending`，余额、批次和流水都不发生部分变化。
- 跨批累计的冻结总成本超过安全四位成本上限时同样整笔回滚，申请单、余额与流水保持原状。
- 并发竞争同一库存时，后到事务等待权威资源锁并重新读取库存；只有库存足够的事务能确认，失败事务不会超卖、负库存或留下流水。
- 本任务只冻结出库成本，没有写项目成本表；项目利润过账保留给 Task 4。

## 确认身份与幂等

- 收货单和出库单分别保存确认幂等键及规范化确认载荷；二者必须同时为空或同时存在。
- `pending` / `rejected` 单据不能携带确认身份；已确认后作废可保留原确认身份，供后续冲销历史使用。
- 同一单据、同一确认键和同一规范载荷可安全重试，只生成一份批次/余额/流水；同键不同载荷稳定冲突。
- 已确认后转为 `void`，完全相同的重试返回当前权威 `void` 单据；不同载荷仍冲突，新键则返回“已经确认”的稳定错误。
- 确认身份一旦写入不可更改；账本流水继续保持追加式不可变。

## 服务层契约

- 新增 `warehouseConfirmationService`，只暴露严格的 `confirmReceipt` 与 `confirmStockOut`。
- 输入、Supabase RPC envelope 和返回 JSON 都采用关闭式、无访问器、无稀疏数组校验；返回值深度冻结。
- 错误只接受匹配的 SQLSTATE、HTTP 状态和稳定数据库 hint；供应商原始错误、价格或身份数据不会透传。
- 供应商错误字段只接受字符串/整数原语；不会对不可信对象执行 `String`、`valueOf` 或 `Symbol.toPrimitive` 强制转换。
- 即使响应数据形状看似有效，只要 HTTP 状态不是 2xx，服务仍按无效响应失败关闭。
- 未配置环境在调用 RPC 前失败关闭；服务不使用 `localStorage`，也没有旧版通用记录回退路径。
