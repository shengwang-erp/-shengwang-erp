# 原始合同直接保存设计

## 目标

取消原始合同会计二次确认。拥有现有项目财务修改权限的用户，只填写含税总金额和税率，系统计算整数日元的税拔金额与税额；合同通过完整校验并由数据库成功返回后，才成为收款计划、合同增减项和实际收款可使用的正式合同。

## 状态兼容

- 保留 `contractConfirmationStatus`、确认人和确认时间等历史字段，不删除、不批量重写。
- 新保存合同继续使用现有项目字段和 `update_project_secure` 接口；数据库中的 `contractRevenueSetupStatus = configured`、有效 schema 版本和完整金额组合共同表示合同已正式保存。
- 旧 `draft`、`confirmed`、`historical_migrated_confirmed` 记录只要金额完整有效，都可用于后续收款业务；临时浏览器草稿不进入项目数据，因此不能参与计算。
- 旧 `confirmed` 和历史确认合同保持原有锁定展示与修改保护；本次不建立新的解锁或改价流程。

## 金额计算

- 输入项依次为“含税总金额（日元）”“税率（%）”。
- `税拔金额 = Math.round(含税总金额 / (1 + 税率 / 100))`。
- `税额 = 含税总金额 - 税拔金额`，保证税拔金额与税额之和严格等于用户输入的含税总金额。
- 税率允许 0，范围仍为 0 至 100；日元金额必须是正整数且为安全整数。
- 输入为空时清空派生显示，不出现 `NaN`；负数、小数日元和非法数字给出中文错误。
- 打开已保存合同时原样保留四个金额字段，不自动重算。若保存值与公式结果仅相差 1 日元，显示取整核对提示；只有用户修改含税总金额或税率后才应用新公式。

## 保存与草稿

- `OriginalContractSection` 等待 `onProjectChange` 的异步数据库结果；只有 RPC 成功返回并更新页面状态后才显示成功并清除浏览器草稿。
- 保存失败保留当前输入和错误信息。
- 浏览器草稿使用 `sessionStorage`，键包含账号和项目 ID，且只保存本表单四个字段；不同账号和项目互不串用。
- 页面恢复时优先恢复同账号、同项目草稿；数据库保存成功后清除。
- 没有项目财务修改权限时前端不提供保存操作；数据库 `update_project_secure` 和收款计划 RPC 继续执行权限校验。

## 下游判断与数据库

- 前端新增统一的 `isOriginalContractSaved(project)`，验证项目 ID、schema、configured 状态、四个金额字段、税率范围和金额加总。
- 收款计划、合同增减项和实际收款统一使用该判断，不再依赖会计确认状态。
- 新迁移在数据库增加等价的私有合同有效性函数，并重建 `replace_project_payment_plan_secure` 的前置判断；其原子保存、已到账期次锁定、比例和金额校验保持不变。
- 不修改已有收款计划、合同增减项或实际到账记录。合同金额变化后，现有差额提示和已到账期次锁定继续生效，不自动重算或覆盖历史记录。

## 验证

- 单元测试覆盖整数计算、0 税率、无效输入、1 日元差异、历史值不重算、正式保存资格判断和旧状态兼容。
- 页面契约测试覆盖输入顺序、只读派生字段、无会计确认按钮、权限和异步保存。
- 草稿测试覆盖账号/项目隔离、失败保留和成功清除。
- 数据库测试覆盖未保存/不完整合同被拒绝、完整旧 draft/confirmed/historical 合同被接受、权限仍被拒绝、已有计划和到账保护不变。
- 运行合同相关测试、数据库静态契约测试、完整测试和生产构建；本轮不执行正式数据库迁移或正式部署。
