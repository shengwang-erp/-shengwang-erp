# 部门打卡模式、定位异常处理与公司人员工资设计

**日期：** 2026-08-12  
**目标工作树：** `/Users/yu/Documents/kaobeierp/warehouse-forward-port`  
**状态：** 用户已逐段确认员工打卡、定位异常、工资统计以及安全验收规则

## 1. 目标

在不复制考勤系统、不污染项目成本的前提下，让“今日打卡”同时适用于工程现场人员和办公室、仓库等非工程人员，并补齐会计处理与工资报表闭环：

1. 工程部必须选择项目打卡，继续使用现场定位、施工点位、工作说明和施工前后照片。
2. 除工程部外，其他部门按当前位置直接上下班打卡，不选择项目，也不填写现场资料。
3. 工程部超出项目打卡范围时先提示但不禁止；员工确认后保留超范围事实，交由会计留痕处理。
4. 定位异常本身不扣工资、不减少人天、不改变项目人工成本，只在工资单中保留处理结论和备注。
5. 非工程人员工资按月统计为公司人员成本，不进入任何工程项目。
6. 支持由管理员将社长等人员设置为免打卡；免打卡人员默认正常全勤计薪，会计仍可进行工资调整。
7. 月度工资明细可按权限查看，并输出为适合 A4 阅读的 Excel、PDF和打印表格。

本设计扩展现有“今日打卡”和“人工考勤与工资”能力。它不建立第二套考勤系统，不伪造办公室项目，也不改变已经确认的历史考勤、工资或项目成本记录。

## 2. 已确认的核心规则

### 2.1 部门与打卡模式

- 服务器以规范人员档案中的当前部门和“需要每日打卡”设置决定打卡模式，浏览器提交的部门、角色或模式不可信。
- `部门 = 工程部` 且需要打卡的人员使用“项目打卡”。
- 除工程部以外、需要打卡的在职人员使用“非项目打卡”。这包括会计、设计、事务、仓库等部门；新增的其他非工程部门也沿用同一规则，不需要逐个硬编码。
- 工程部可以从全部符合现有打卡条件的项目中选择，不要求先分配为项目人员。
- 工程部没有合适现场时仍必须选择项目。用户后续可以建立一个长期、具有固定打卡地址的项目供这类人员使用；本期不增加“无项目工程打卡”。
- 任一需要打卡的员工同一时刻最多一个开放场次；同一天可以依次完成多个场次。
- 所有工作日期和可信打卡时间继续由服务器按 `Asia/Tokyo` 计算。

### 2.2 工程部项目打卡

- 员工上班前必须选择一个状态和定位均符合现有打卡条件的项目。
- 每次上班或下班均重新取得当前位置，不复用旧定位。
- 保留现有项目场次完整流程：施工点位、工作说明、开工前照片和完工照片。
- 下班前仍须至少有一个完整点位，具体完整性规则沿用现有“今日打卡”设计。
- 上班和下班的范围判定都由服务器根据项目定位快照、项目半径、设备位置和定位精度计算。
- 范围内直接保存为正常打卡。
- 超出范围时不再要求员工填写异常原因。页面显示一次确认提示，至少说明所选项目、允许范围、实际距离和“仍然打卡后会记录为超范围”。
- 员工可以取消并重新定位，也可以选择“仍然打卡”。确认后打卡成功，事件保存为超范围定位事实。
- 该确认只表示员工知晓并坚持提交，不能把超范围事件改成正常事件。

### 2.3 非工程人员打卡

- 页面不显示项目选择、施工点位、工作说明、施工前后照片或项目成本提示。
- 员工取得当前位置后直接执行上班或下班打卡。
- 上下班均保存设备位置、定位精度、设备时间和服务器时间，但不与办公室、仓库或项目地址做范围比较。
- 非项目场次不保存虚拟项目，不产生项目人工成本分摊，不出现在项目成本明细中。
- 事务、设计等人员即使直接外出办事或先去现场，也按相同的当前位置流程打卡，不需要外勤申请、预先审批或原因输入。
- 仓库人员在本期也使用非项目打卡；仓库地址可以作为管理参考，但不作为强制范围。

### 2.4 定位失败

- 所有需要打卡的人员都必须成功取得有效设备位置。
- 拒绝定位、超时、坐标非法、定位精度非法或浏览器不支持定位时，均不允许提交打卡。
- 页面显示明确的中文原因和重试操作；不得用填写备注、异常原因或选择非项目模式绕过定位。

### 2.5 免打卡人员

- 人员管理增加由管理员维护的“需要每日打卡”设置，普通在职员工默认开启。
- 只有具备人员管理更新权限的管理员可以修改；员工本人不能修改。
- 社长可关闭该设置，成为免打卡人员；本设计不把职位名称硬编码为自动免打卡，最终以管理员设置为准。
- 免打卡人员不生成虚假上下班事件，也不产生未打卡、迟到、早退、未下班等考勤异常。
- 月度工资按正常全勤和人员档案中的工资标准计算；会计仍可录入加班费、奖金、扣款和备注等现有工资调整。
- 设置只影响其生效后的未确认日期。已经确认或月结锁定的历史快照不回写、不重算。

## 3. 选择的架构方案

采用同一考勤域中的显式双模式：

- `project`：工程部项目打卡；包含项目快照、距离判定、工作点位和照片，可形成项目人工成本。
- `general`：非工程人员非项目打卡；包含上下班时间和设备定位，不包含项目字段、工作点位或照片，只形成公司人员考勤和工资事实。

不采用以下方案：

- 不为办公室、仓库或社长创建虚拟项目。虚拟项目会把公司工资混入项目成本，也会让项目报表难以解释。
- 不建立第二套办公室考勤表和页面。两套系统会重复人员、时间、工资、月结、权限和审计逻辑。
- 不允许工程部留空项目打卡。工程人员成本必须具有明确项目归属；无固定现场时由业务建立长期项目解决。

共享同一考勤域可以复用开放场次约束、幂等请求、定位采集、每日状态、工资核算、权限和审计，同时通过明确模式阻止非项目工资流入项目成本。

## 4. 员工页面流程

### 4.1 页面初始化

服务器返回当前员工最小必要打卡策略：

- 员工规范身份；
- 是否需要每日打卡；
- 服务器判定的打卡模式；
- 当前开放场次及当日历史；
- 项目模式下的可选项目。

客户端只根据该策略渲染流程。即使客户端被篡改，写入 RPC 仍重新读取规范人员档案并执行相同规则。

### 4.2 工程部流程

1. 选择一个可打卡项目。
2. 点击上班打卡并取得实时位置。
3. 服务端计算范围：正常则写入；超范围则返回“需要确认”而不写入事件。
4. 页面显示超范围确认框。取消时保留项目选择并允许重新定位；确认时使用同一请求编号重试。
5. 服务端重新验证身份、部门、项目和位置后写入超范围事件。
6. 员工填写施工点位、工作说明和施工前后照片。
7. 下班时再次定位并执行同样的正常/超范围流程。

### 4.3 非工程人员流程

1. 页面直接显示上下班状态和主操作按钮。
2. 点击打卡后取得实时位置。
3. 服务端确认该员工属于非工程部门且需要打卡，写入非项目上班或下班事件。
4. 上班后页面只显示上班时间、定位已记录状态和下班操作，不显示现场资料编辑区。

### 4.4 免打卡页面状态

免打卡人员打开“今日打卡”时显示“当前账号已由管理员设置为免每日打卡，工资按月度规则核算”，不显示可提交打卡的主按钮。历史记录仍按原权限可读。

## 5. 超范围事实与会计处理

### 5.1 原始事实

工程项目的正常或超范围结果由服务器计算。超范围事件至少保留：

- 员工和项目快照；
- 上班或下班事件类型；
- 服务器记录时间与设备时间；
- 实际经纬度和定位精度；
- 项目中心、项目半径和服务端计算距离；
- 员工已确认仍然打卡的标志与确认时间。

普通员工和会计都不能覆盖上述原始事实。

### 5.2 会计待处理

- 任一上班或下班事件超范围，当天进入“定位异常待处理”。
- 会计日结显示原始事件、项目、时间、半径、距离和员工确认状态。
- 会计必须选择一个定位处理结论：
  - `确认有效`：超范围具有合理情况；
  - `判定异常`：保留为工资单定位异常记录。
- 两种结论都不自动扣工资、不减少人天、不改变最终项目人工成本。
- 会计仍按现有日结规则选择整天、半天、休息、请假、调休或缺勤；定位处理结论不替代出勤核算类型。
- 只要当天包含超范围事实，确认日结前必须选择定位处理结论并填写非空处理备注。
- 保存草稿可以暂存处理结论和备注，但在要求未满足前不能确认。
- 确认后保存处理人、处理时间、结论、备注和原始异常快照；月结锁定后遵守现有重新打开与审计规则。

### 5.3 工资单展示

- `确认有效`：工资单可显示“超范围已核实有效”，不列为未处理风险。
- `判定异常`：工资单显示“超范围打卡”及会计备注，但金额与正常出勤核算结果相同。
- 工资表中的定位异常是管理记录，不是纪律处分或自动扣款依据。

## 6. 工资与成本口径

### 6.1 工程人员

- 工资继续使用现有月薪、日薪、时薪和会计日结规则。
- 已确认的人天和最终项目人工成本按现有项目分摊进入相应项目。
- 超范围处理结论不改变分摊金额；如需调整人天或工资，会计必须使用现有日结或月度工资调整字段并留下对应备注。

### 6.2 公司人员

- 除工程部以外的人员工资统一统计为“公司人员工资”。
- 非项目打卡提供出勤事实，但不会自动创建项目分摊；其项目人工成本固定为零。
- 工资金额计入公司人员成本，供经营费用、月度工资和领导报表汇总使用，不进入任何项目成本。
- 免打卡人员按正常全勤进入公司人员工资；工资类型与金额仍取人员档案和确认时快照。
- 若未来需要把某位非工程人员的部分工资分配到项目，必须另行设计明确的会计分摊功能，本期不自动推断。

### 6.3 月度工资统计

月度工资页面支持按月份、部门、员工和状态查看。至少展示：

- 员工编号、姓名、部门、职位；
- 考勤方式：项目打卡、非项目打卡或免打卡；
- 应出勤、整天、半天、休息/请假/调休、缺勤；
- 迟到、早退、超范围打卡和加班待确认次数；
- 基本工资、加班费、奖金、扣款、实发工资；
- 项目已分摊金额或公司人员成本；
- 月度状态和会计备注。

工资标准缺失、待处理日结、未平衡项目分摊或未处理加班时，继续沿用现有规则阻止月度确认。

## 7. 报表输出

- 月度工资支持导出 Excel、导出 PDF和打印。
- 导出内容跟随当前月份、部门、员工和状态筛选，不默认导出全部历史。
- 报表明确区分工程人员项目成本与公司人员成本，并显示当月合计。
- 超范围记录在明细或备注区域展示处理结论，不改变工资金额合计。
- 输出使用白底、深色正文和克制的灰色分隔，适配 A4 原色打印，不使用网页黑金背景。
- 字体适中、行高舒展、表头和合计区明确；列宽按内容分配，避免过密、截断和无意义横向压缩。
- Excel 保持数字和日期为可编辑的原生单元格，金额使用日元格式，冻结表头，设置打印区域、重复表头和页边距。
- PDF与打印显示报表名称、统计月份、筛选条件、生成时间、记录数量、页码和签字区。
- 导出权限与页面工资权限一致；无工资查看权限的账号不能通过导出获得金额。

## 8. 数据模型演进

具体迁移名称在实施计划中确定，模型应满足以下语义。

### 8.1 人员打卡策略

在规范人员档案中增加受权限保护的每日打卡设置：

```text
attendance_required boolean not null default true
attendance_policy_updated_at timestamptz
attendance_policy_updated_by uuid
```

如现有人员架构更适合独立策略表，可以使用一对一规范表，但服务器返回和审计语义必须相同。设置变更由安全 RPC 完成并写审计。

### 8.2 统一考勤场次

现有 `project_attendance_sessions` 演进为支持显式模式的统一场次，或迁移至语义等价的新规范表：

```text
attendance_mode text not null check in ('project', 'general')
project_id text null
project_*_snapshot null
```

数据库约束必须保证：

- `project` 场次的项目、地址、坐标和半径快照全部非空；
- `general` 场次的所有项目和半径字段全部为空；
- 每名员工最多一个开放场次；
- 工作日期、开放与关闭时间状态一致；
- 已有历史项目场次迁移后全部标记为 `project`，不改变其快照和事件。

### 8.3 统一考勤事件

事件同时支持两类场次：

- 项目事件保留距离、半径、正常/超范围结果；
- 非项目事件保留位置和精度，距离、半径为空，结果为不参与范围判断的明确状态，不能伪装成项目正常事件；
- 超范围确认使用结构化字段，例如确认标志和服务器确认时间，不再依赖员工自由填写异常原因；
- 原有异常原因保留用于历史兼容和只读展示，不删除历史文本。

### 8.4 定位处理结论

日结保存显式的定位处理结论，不能仅从自由文本推断：

```text
location_review_status text null check in ('confirmed_valid', 'recorded_abnormal')
location_review_note text not null default ''
location_reviewed_by uuid
location_reviewed_at timestamptz
```

只有存在超范围事实的日结需要该结论。确认时数据库验证结论和非空备注；工资和人天仍由独立的 `resolution_type` 与 `attendance_units` 决定。

月度工资快照保存当月超范围记录数量和展示摘要，保证人员档案或日结之后变化时，已确认工资单仍可追溯。

## 9. 服务端边界

服务端接口可以在现有安全 RPC 上演进，但必须提供以下职责：

- 读取当前员工的服务器判定打卡策略和当日场次；
- 列出工程部可选择的全部有效项目；
- 创建项目场次或非项目场次，并拒绝部门与模式不匹配的请求；
- 项目超范围且未确认时不写事件，返回稳定的“需要确认”业务错误；
- 确认重试时重新计算距离，并仅在仍超范围时写入结构化确认事实；若重新计算已在范围内则保存为正常；
- 非项目打卡拒绝项目参数，且不生成项目快照或分摊；
- 工程部的下班接口继续验证完整施工点位；非项目下班不执行点位或照片检查；
- 会计日结确认时校验定位处理结论与备注；
- 月度工资根据考勤方式计算公司人员与工程人员数据，并生成权限裁剪后的报表模型。

所有写请求使用唯一请求编号和事务锁。第一次超范围检查未写入业务事件，因此确认重试可安全复用同一请求编号；成功写入后再次重试必须返回同一结果，不能产生重复场次或事件。

## 10. 权限、安全与审计

- 打卡身份、部门、免打卡状态、项目快照、服务器时间、距离、结果、员工确认和会计处理人均由服务器决定。
- 普通员工不能修改或删除成功保存的上下班位置、时间或范围结果。
- 人员管理更新权限控制“需要每日打卡”设置。
- 现有人工核算更新权限控制定位异常的会计处理；工资和项目金额继续受工资敏感权限及项目成本权限保护。
- 免打卡不能作为员工自选模式，也不能通过前端隐藏字段绕过。
- 会计处理、工资确认、月结重新打开和打卡策略变更均写仅追加审计日志。
- 已确认或月结锁定的数据保留快照；后续部门、职位、项目定位或打卡策略变化不改写历史。
- 读取接口只返回调用者需要的字段，定位坐标等敏感事实只在既有本人或管理查看范围内提供。

## 11. 错误处理与兼容

- 定位服务失败：不写入，显示中文重试提示。
- 部门或策略已被管理员修改：服务端拒绝旧页面请求，客户端刷新策略并切换正确流程。
- 项目失效或定位被取消：工程打卡拒绝提交并要求重新选择项目。
- 超范围确认期间位置变化：服务端以确认请求中的有效定位事实重新计算，不信任前端展示结果。
- 重复点击或网络重试：返回同一成功结果，不重复写入。
- 服务不可用：不回退到浏览器本地数据作为正式考勤。
- 开放场次存在：不允许另开项目或非项目场次。
- 非项目场次不完整：只要求有效上下班定位，不因缺少工作点位或照片报错。
- 历史项目打卡、员工填写的异常原因、已确认日结、工资和项目分摊全部保留。
- 迁移发布顺序必须兼容旧前端和新数据库的短暂交叠，避免部署期间旧页面把新模式记录解析为无效数据。

## 12. 测试与验收

### 12.1 领域与服务测试

- 工程部、非工程部、免打卡人员的策略判定；
- 管理员变更策略及未授权修改被拒绝；
- 项目/非项目场次约束和历史迁移；
- 工程部必须选择有效项目，非工程人员不能伪造项目模式；
- 上下班范围内、超范围取消、确认后成功、确认重试和重复请求；
- 所有部门的定位拒绝、超时、非法坐标和非法精度；
- 工程下班点位/照片完整性与非项目下班免现场资料；
- 超范围事实不可变、会计两种处理结论、必填备注和审计；
- 两种定位处理结论均不改变工资、人天或项目成本；
- 非项目工资进入公司人员成本且项目分摊为零；
- 免打卡人员无缺卡异常并按全勤进入月度工资；
- 历史项目场次、历史异常原因和已锁定工资兼容。

### 12.2 页面测试

- 工程部看到项目和现场资料流程；非工程部门只看到简化上下班；免打卡人员看到说明状态；
- 超范围确认框信息完整、取消和“仍然打卡”行为正确；
- 定位失败提示清楚且不会产生记录；
- 会计日结显示只读定位事实、处理结论与必填备注；
- 月度工资表正确显示考勤方式、公司人员成本和定位异常记录；
- 工资敏感权限和项目成本权限在页面与导出中一致；
- 桌面和手机常用宽度下操作清晰，不出现关键按钮遮挡或不可读表格。

### 12.3 输出测试

- Excel、PDF和打印内容跟随当前筛选；
- 工程人员、公司人员和免打卡人员金额及合计与页面一致；
- 定位异常结论不改变金额，但正确进入备注；
- Excel 日期、金额和数字单元格类型正确且可编辑；
- A4页面方向、页边距、列宽、重复表头、页码、签字区和分页正确；
- 空结果、长姓名、长部门、长备注和多页数据仍保持工整可读。

### 12.4 发布验收

上线前必须完成：

1. 聚焦自动化测试；
2. 完整测试套件；
3. 生产构建；
4. 数据库迁移的前向兼容和回滚检查；
5. 电脑端与手机端真实浏览器验证；
6. 工程范围内、工程超范围、非工程打卡、免打卡、会计处理和工资导出的端到端检查；
7. 部署后生产域名、认证、数据库连接和关键控制台错误复核。
