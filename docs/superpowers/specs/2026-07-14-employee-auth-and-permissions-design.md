# 员工编号、Supabase Auth 与部门/职位权限设计

**日期：** 2026-07-14

**状态：** 已经用户逐段确认，等待书面规格复核

**范围：** 员工创建、员工编号、登录与会话、账号停用、部门/职位权限、人员管理界面、安全迁移与测试

## 1. 背景

现有 ERP 是 React + Vite 单页应用。当前登录逻辑在浏览器中按姓名查找员工并直接比较 `passwordHash`；身份和权限快照保存在 `localStorage.currentUser`。浏览器在登录前即可使用公开 key 读取通用 JSONB 业务表，而现有 RLS 策略条件恒为 `true`。源码和建表脚本还包含固定恢复账号及其明文密码。

本次改造把身份认证迁移到 Supabase Auth，把员工编号、账号状态和权限判断移到数据库及 Supabase Edge Functions。浏览器仅持有 Supabase 公开 key 和用户会话，绝不接收 service-role key。

## 2. 已确认的业务规则

### 2.1 员工编号

- 隐藏超级管理员固定使用 `SW-000`。
- `SW-000` 不进入正式员工编号序列，也不显示在普通员工列表或人员统计中。
- 正式员工由数据库从 `SW-001` 开始并发安全地顺序生成。
- 编号创建后不可修改、不可复用；被停用或删除的员工仍永久占用原编号。
- 编号至少补齐三位，但超过 999 后自然扩展，例如 `SW-1000`。
- 外部 Auth 创建或资料创建失败后，已经预留的编号不重新分配。序列允许因失败产生间隔，以换取并发安全和永不复用。

### 2.2 固定部门

数据库和服务端只接受以下值：

1. 总务部
2. 营业部
3. 事务部
4. 后勤部
5. 设计部
6. 工程部
7. 仓库管理部
8. 电商部
9. 采购部
10. 财务部

### 2.3 固定职位

数据库和服务端只接受以下值：

1. 社长
2. 总务部长
3. 营业部长
4. 部长
5. 主任
6. 主任设计师
7. 设计师
8. 仓库管理员
9. 工事部长
10. 职长
11. 大工
12. 中工
13. 小工
14. 会计主管
15. 会计

### 2.4 权限来源

- 不再给员工设置个人角色、个人模块权限或个人例外。
- 权限只配置在部门模板和职位模板上。
- 员工有效权限为“部门权限与职位权限的并集”。任一模板授予某权限即生效；本期不设计显式拒绝规则。
- 调整部门、职位或权限模板后，下一次受保护请求立即使用新权限，不保留旧权限快照。
- 新员工没有个人权限；其可用权限完全取决于当时对应的部门和职位模板。若两个模板都未授予权限，登录后只能看到“尚未配置权限”的状态页和改密/退出入口。
- `SW-000` 始终拥有全部系统权限，不依赖模板。
- 职位为“社长”的在职、启用账号始终拥有员工创建、员工部门/职位维护、账号管理和权限模板管理权；其他业务模块仍按部门/职位模板决定。
- 只有 `SW-000` 和职位为“社长”的账号可以创建员工、修改员工部门或职位、启停账号、重置临时密码及维护权限模板。
- 迁移只创建固定部门和职位的空模板，不猜测各部门的具体业务授权；除上述固定管理规则外，初始权限均为空，由 `SW-000` 或社长在权限模板界面配置。

### 2.5 账号状态

- 只有 `employment_status = '在职'` 且 `account_status = 'active'` 的员工可以访问受保护数据。
- 离职、休假、停工、账号停用、资料软删除或 Auth 关联缺失均视为不可访问。
- `SW-000` 不允许被普通管理操作删除、停用、改号或取消隐藏。

## 3. 总体架构

### 3.1 浏览器

浏览器只负责：

- 收集员工编号和密码；
- 调用 Edge Functions；
- 保存 Supabase Auth 的标准 access token 和 refresh token；
- 按服务端返回的当前员工资料和有效权限渲染界面；
- 使用带用户 JWT 的 Supabase 请求访问经过 RLS 保护的业务数据。

浏览器不再：

- 下载员工密码字段；
- 比较密码；
- 根据姓名建立身份；
- 使用可伪造的 `localStorage.currentUser` 作为安全依据；
- 自行生成员工编号；
- 自行决定操作者身份或可信权限；
- 接收或构建 service-role key。

### 3.2 Supabase Edge Functions

Edge Functions 分为边界清晰的服务：

- `employee-login`：员工编号登录、限速、账号状态预检、派生内部 Auth 标识并建立会话。
- `employee-provision`：创建员工、生成编号与初始密码、创建 Auth 用户、创建资料及失败补偿。
- `employee-admin`：员工资料修改、部门/职位调整、账号启停和临时密码重置。
- `employee-change-password`：已登录员工首次改密或主动改密。
- `permission-templates`：读取和维护部门/职位权限模板。
- `employee-bootstrap-admin`：仅部署期使用的一次性 `SW-000` 引导入口或本地管理脚本；完成后不可公开调用。

所有需要管理员权限的函数均使用用户 JWT 验证调用者，再从数据库重新读取调用者员工资料和当前状态。函数不能信任请求体中的角色、职位、员工编号或操作者字段。

### 3.3 数据库与 RLS

数据库是员工状态、部门、职位和权限的唯一可信来源。业务表继续由浏览器以 authenticated JWT 访问，但所有恒真原型策略必须替换为严格 RLS。每条策略都调用服务端权限函数，重新确认：

1. `auth.uid()` 是否关联员工；
2. 员工是否在职；
3. 账号是否启用；
4. 是否需要先修改临时密码；
5. 当前部门和职位是否具备本次表与动作所需权限。

service-role 只在 Edge Function 的服务端秘密环境中使用，并绕过 RLS，因此每个 Edge Function 必须显式完成上述身份与授权检查。

## 4. 数据模型

### 4.1 `employee_profiles`

新建规范化员工主表，替代旧通用 `employees.payload` 作为员工与认证的可信来源。关键字段包括：

- `id uuid primary key`
- `employee_number text not null unique`
- `auth_user_id uuid unique references auth.users(id) on delete set null`
- `name text not null`
- `department text not null`
- `position text not null`
- `employment_status text not null`
- `account_status text not null`
- `must_change_password boolean not null default true`
- `is_hidden_system_account boolean not null default false`
- 现有员工档案、身份、工资字段
- `created_at`、`updated_at`
- `created_by_auth_user_id`、`updated_by_auth_user_id`

部门、职位、员工状态和账号状态均有数据库 CHECK 约束。`employee_number` 由触发器保护，插入后任何普通更新都不得改变。

authenticated/anon 角色不直接获得该表的通用增删改权限。普通员工目录通过只返回员工编号、姓名、部门、职位和状态的安全 RPC/视图提供；完整档案通过受权限检查的服务读取，工资和证件字段在返回前单独检查敏感权限。

### 4.2 `employee_number_sequence`

正式员工编号使用 PostgreSQL sequence 或等效的数据库计数设施，从 1 开始。数据库函数把数值格式化为 `SW-` 加至少三位数字。`SW-000` 由引导流程显式创建，不调用该序列。

### 4.3 `employee_provisioning_requests`

记录员工创建编排状态和幂等键：

- `request_id uuid unique`
- `employee_number text unique`
- `status`：`reserved`、`auth_created`、`completed`、`compensation_pending`、`compensated`、`failed`
- `auth_user_id uuid null`
- 安全的错误代码与时间戳

禁止保存初始密码、内部 Auth 标识或请求原文。相同 `request_id` 重试不得创建第二名员工。若原响应丢失，服务端不尝试恢复旧明文密码；管理员使用“重置临时密码”生成新的单次显示密码。

### 4.4 `permission_grants`

权限按模板记录：

- `subject_type`：`department` 或 `position`
- `subject_code`：固定部门或职位值
- `permission_key`：稳定的英文权限代码
- 主键为 `(subject_type, subject_code, permission_key)`

权限键覆盖现有所有业务模块的 `view`、`create`、`update`、`delete`，并包含工资、证件、合同金额、利润、采购付款等敏感读取/修改权限。界面显示中文标签，数据库使用稳定代码。

`has_current_permission(permission_key)` 在函数内部只使用 `auth.uid()`，以 SECURITY DEFINER 方式读取当前员工和两个模板，并返回并集结果。调用者不能传入其他用户 ID。函数固定 `search_path`，只授予必要执行权限。`SW-000` 返回全部允许；社长的员工与模板管理权限由服务端固定规则授予。

### 4.5 `auth_login_attempts` 与审计

登录接口按“员工编号 + 网络来源的不可逆摘要”记录短期失败次数和锁定时间，不记录密码。默认策略为 15 分钟内连续 5 次失败后锁定 15 分钟；成功登录后清除对应失败计数。所有员工创建、启停、调岗、权限模板修改和密码重置均写服务端审计记录，操作者来自已验证的 `auth.uid()`。

## 5. 员工创建流程

1. 浏览器生成一次性 `request_id` 并提交员工档案；部门和职位必填，不能提交员工编号、Auth 标识或权限。
2. `employee-provision` 验证 JWT，并重新确认调用者是 `SW-000` 或在职、启用的社长。
3. 服务端校验固定字典和档案字段。
4. 数据库以幂等方式预留下一个 `SW-xxx` 编号。
5. 服务端使用 Web Crypto 生成 12 位随机临时密码，至少包含大写字母、小写字母和数字，并排除容易混淆的字符。
6. 服务端以 HMAC-SHA256 和仅存在于 Edge secret 的派生密钥，从规范化员工编号生成不透明的 Auth 内部标识。该标识只供 Supabase Auth 使用，不出现在人员界面、员工资料或业务 API 返回中。
7. 独立的 admin client 调用 Supabase Auth `admin.createUser`；内部认证标识自动确认，密码只传给 Auth。
8. Auth 创建成功后插入 `employee_profiles` 并关联 `auth_user_id`。
9. 资料插入失败时立即调用 `admin.deleteUser` 删除本次创建的 Auth 用户。删除失败则把请求标记为 `compensation_pending`，供受控重试任务处理，并向管理员返回明确失败状态。
10. 全部成功后，响应只返回一次员工编号和临时密码。前端将它们保存在当前组件内存中，提供复制按钮；弹窗关闭或页面离开后清除，不能写入 localStorage、日志、分析事件或数据库。

数据库序列分配发生在 Auth 调用前，因此失败创建可能留下编号间隔；间隔不回收。

## 6. `SW-000` 引导

- 引导流程只在部署时由受控服务端命令或一次性函数运行。
- `SW-000` 的密码保持用户指定的现有值，但该值不得写入本规格、源码、SQL、Git 管理的配置、前端变量或日志。
- 部署人员通过短期服务端 secret 提供该密码；引导完成后删除该 secret。
- Supabase Auth 只保存其密码散列。
- `SW-000` 不要求首次修改密码，但允许以后主动修改。
- 由于现有密码过去曾存在于源码和构建产物中，这是用户明确接受的遗留风险。登录限速、失败锁定和审计仍必须实施。
- 引导必须幂等：若 Auth 用户或资料已存在，只验证关联，不重置密码或重复创建。

## 7. 登录、改密与会话

### 7.1 登录

1. 登录页仅提交 `employeeNumber` 和 `password`。
2. `employee-login` 规范化大写编号并要求匹配 `^SW-\d{3,}$`。
3. 接口执行限速，再按员工编号读取资料，确认员工存在、在职、账号启用且已关联 Auth。
4. 接口用与创建时相同的 HMAC 派生内部 Auth 标识。
5. 使用不含 service-role 的独立 Auth client 调用 `signInWithPassword`。
6. 成功后只返回建立标准 Supabase 会话所需的 token 字段；错误响应不返回内部 Auth 标识。Supabase Auth 可能把这个不透明别名放入 JWT claim，因此它不是秘密；它不得包含真实邮箱、手机号或其他个人信息，也不得由界面显示或作为业务身份依据。
7. 浏览器调用 `setSession`，随后获取当前员工资料和有效权限。只有认证状态确定后才挂载业务数据 hooks。

登录页不得出现姓名、手机号、邮箱、注册或忘记密码自助入口。

### 7.2 首次改密

- 除 `SW-000` 外，新员工和被管理员重置密码的员工均设置 `must_change_password = true`。
- 登录成功后只能访问改密、退出和最小当前用户接口；业务 RLS 在改密完成前拒绝其他操作。
- 改密成功后由服务端更新 Auth 密码，再把 `must_change_password` 设为 `false`。

### 7.3 停用与即时失效

- 停用时先把数据库 `account_status` 改为 disabled，再调用 Auth 管理接口封禁用户并撤销可撤销会话。
- 即使旧 access token 在短时间内仍未过期，RLS 每次请求都会读取数据库当前状态，因此所有后续受保护请求立即被拒绝。
- 前端收到 401/403 或当前员工状态校验失败时清除 Auth 会话和业务内存数据，返回登录页。
- 重新启用时先解除 Auth 封禁，再把数据库账号状态设为 active；任一步失败都保持安全的不可访问状态并记录审计。

## 8. 人员管理与权限界面

### 8.1 登录页

- 保留当前黑金视觉风格和企业标识。
- 字段只有“员工编号”和“密码”。
- 员工编号示例为 `SW-001`。
- 错误信息区分“账号已停用/当前不可登录”和通用“员工编号或密码错误”，不泄露内部 Auth 标识。

### 8.2 新增/编辑员工

- 新增表单显示只读提示“员工编号将在保存成功后自动生成”。
- 部门和职位使用固定下拉选项并设为必填。
- 保存期间禁用重复提交；只有服务端全部完成后才把员工加入列表。
- 创建成功弹窗显示员工编号、一次性初始密码、分别复制和全部复制按钮，并要求管理员确认已经安全交付。
- 编辑表单显示只读员工编号；服务器拒绝任何修改编号的请求。
- 删除原“登录账号”“明文密码”“权限角色”和员工个人权限勾选项。
- 增加账号启用/停用和“生成新临时密码”操作。重置结果同样只显示一次。
- `SW-000` 不出现在普通员工列表，且不能通过普通员工接口编辑。

### 8.3 权限模板

- 人员管理或系统设置中增加“部门权限”和“职位权限”两个配置区。
- 每个固定部门/职位显示现有模块与动作矩阵；保存采用服务端事务替换该模板的授权集合。
- 只有 `SW-000` 和社长看得到并可提交该配置区。
- 不提供员工个人权限入口。

### 8.4 数据可见性

- 普通业务选择器只读取安全员工目录。
- 人员档案详情、工资、护照、在留卡和住址分别按当前有效权限裁剪。
- 未授权字段不只是界面隐藏，服务端响应本身不得包含这些值。

## 9. 迁移设计

1. 备份并审计线上实际 schema 和数据；仓库当前没有可验证的线上 Supabase 配置，不能假设线上完全等同于原型 SQL。
2. 新建规范化表、权限表、编号设施、幂等/补偿表、审计表和权限函数，暂不开放给 anon。
3. 部署 Edge Functions 和 `SW-000` 引导流程。
4. 使用短期服务端 secret 引导 `SW-000`，确认可以建立 Auth 会话。
5. 对旧 `employees` JSONB 数据生成迁移报告：检查 `record_key`/`payload.employeeId` 不一致、混合编号、重复姓名、删除状态和业务引用。
6. 如存在历史员工，为其建立 `legacy_employee_id` 映射；不自动原地重写所有业务 JSON 中的旧员工编号。需要登录的历史员工由管理员逐一确认并生成新的 Auth 临时密码。
7. 从旧员工 payload 中删除 `passwordHash`、`username` 等认证字段，并移除旧恢复账号记录。旧通用 `employees` 表停止作为可信员工源并撤销浏览器直接访问。
8. 部署新前端，移除默认管理员自愈、自助注册、姓名登录和 `localStorage.currentUser`。发布时清理已知旧认证缓存和员工密码缓存。
9. 将所有业务表的恒真原型 RLS 策略替换为 authenticated + 当前状态 + 权限函数策略，并撤销 anon 业务表权限。
10. 验证新版本后删除一次性引导入口和短期 secret。

迁移需要短维护窗口；新严格 RLS 与新前端必须协调发布。未配置 Supabase 或服务端函数不可用时应用应失败关闭并显示“认证服务未配置/暂不可用”，不得退回本地明文登录或本地业务缓存写入。

## 10. 错误处理

- 所有 Edge Functions 返回稳定错误代码和面向用户的中文消息，不把内部 Auth 标识作为独立业务字段返回，也不返回堆栈、服务端密钥或供应商原始敏感响应。
- 创建请求通过 `request_id` 幂等；网络重试不会创建重复员工。
- 只有服务端创建完成后前端才更新列表，不做不可回滚的乐观新增。
- Auth 已创建但资料失败时执行删除补偿；补偿失败进入可审计、可重试状态。
- 一次性密码不能通过日志、异常监控、数据库或重试接口恢复；丢失时生成新的临时密码。
- 权限、部门、职位和状态修改均由数据库约束与服务端授权双重校验。
- 任何受保护请求的状态或权限校验失败都不得静默退回 localStorage 数据。

## 11. 测试与验收

### 11.1 单元测试

- 员工编号规范化、格式化和超过 999 的行为。
- 固定部门/职位校验。
- 随机密码字符集和组成规则。
- HMAC 内部标识的确定性、不同编号隔离，以及不出现在业务 payload 或界面中。
- 部门/职位权限并集，无个人权限。
- `SW-000` 和社长的固定管理规则。
- 错误映射及敏感字段清理。

### 11.2 数据库与 RLS 集成测试

- 并发预留不产生重复编号，`SW-000` 不消耗序列。
- employee_number 插入后不可修改，非法部门/职位被数据库拒绝。
- anon 无法读取或写入业务表、员工主表和权限表。
- 在职启用、停用、离职、未改临时密码等账号的访问矩阵。
- 部门和职位模板变化在下一请求生效。
- 未授权员工无法修改部门、职位、账号状态或权限模板。
- 敏感员工字段不会通过安全目录或未授权详情接口泄露。

### 11.3 Edge Function 集成测试

- 正确、错误、未知和停用账号登录。
- 限速和连续失败锁定。
- Auth 创建成功/资料成功的完整创建流程。
- Auth 创建成功/资料失败时调用 Auth 删除补偿。
- 补偿删除失败时记录 `compensation_pending`。
- 相同幂等键重试不创建第二名员工。
- 临时密码只在首次成功响应或重置响应出现。
- service-role key 不出现在任何客户端响应。

### 11.4 前端与浏览器测试

- 登录页只有员工编号和密码，无姓名、手机、邮箱及注册入口。
- 未认证时不发起业务表读取。
- 创建表单部门/职位必选，编号只读。
- 创建成功和重置密码的一次性凭据弹窗。
- 权限模板矩阵只有 `SW-000`/社长可见。
- 调岗或停用后下一请求立即更新界面或退出登录。
- `SW-000` 始终不出现在员工列表和统计。
- 手机和桌面布局均可操作。

### 11.5 构建安全检查

- 运行全部现有测试和新增测试。
- 生产构建成功。
- 扫描源码和 `dist`，确认没有 service-role key、引导密码、旧恢复账号明文、`passwordHash` 或默认本地会话逻辑。
- 浏览器实际验证登录、创建员工、一次性密码、权限变化和停用即时失效。

## 12. 非目标

- 不提供员工自助注册。
- 不支持手机号或邮箱作为登录输入。
- 不提供个人权限覆盖或显式拒绝规则。
- 不保证失败创建完全无编号间隔。
- 不在本期自动重写所有历史业务记录中的旧员工编号。
- 不在浏览器或 Git 仓库保存 `SW-000` 的实际密码。
