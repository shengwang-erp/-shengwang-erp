# 仓库管理模块向线上第二版安全移植设计

**日期：** 2026-08-06

**状态：** 用户已确认采用“以线上第二版为底板、只移植仓库功能白名单”的方案

## 1. 目标与不可违反的边界

把已经开发完成的仓库管理业务能力加入当前线上第二版 ERP，同时保留第二版现有登录、人员、项目、采购、会计、考勤、权限和数据安全体系。

本次不是合并旧系统，也不是复制整个仓库开发分支。线上第二版提交 `d5953c546996dc9af73326fbe21c36062dca46d0` 是唯一底板；仓库开发提交 `07f478957b51f8393b4ad918de3329563fcdb601` 只是只读功能来源。两者共同祖先为 `4d1930e68049721cb39e994072b85cf87847f5c4`，已确认存在较大分叉，因此禁止整体 merge、整体 cherry-pick 或用旧文件覆盖新版文件。

首轮只做隔离本地开发和验收，不部署线上，不修改线上 Supabase，不迁移任何旧库存或测试库存。当前第二版本地脏工作区保持原样，不在其中开发。

## 2. 采用的移植方式

采用受控前向移植（controlled forward-port）：

1. 从线上第二版准确提交建立独立分支 `codex/warehouse-forward-port`。
2. 以文件和功能白名单识别仓库领域代码。
3. 可独立复用的仓库纯业务代码及测试逐项移植。
4. 与旧系统连接的导航、身份、权限、持久化、采购、项目成本和 Supabase 逻辑全部舍弃旧连接，按照第二版架构重新实现适配层。
5. 每个功能先补第二版契约测试，再接入页面或数据库。
6. 完成后使用反向差异审计证明没有携带旧版公共模块。

不采用整体分支合并，因为它可能把旧登录、旧会话、旧持久化和旧页面壳带入第二版；也不完全重写仓库领域，因为那会浪费已有且经过多轮修复的仓库业务规则和测试。

## 3. 代码迁移白名单与禁用清单

### 3.1 可作为移植候选的仓库专用内容

- `src/features/warehouse/` 中的物品档案、规格、库存、操作、报表、二维码、照片、日期、权限领域函数、页面组件、样式和测试。
- 仓库专用服务中的确认、库存流水、请求暂存及仓库数据库契约测试。
- 仓库专用 SQL 中的数据模型、确认事务、流水、幂等、安全和最终修复规则。
- 原设计文档与测试用例中的业务规则。

候选不代表自动复制。每个文件仍需检查依赖；依赖旧版公共服务的部分拆除后才能进入第二版。

### 3.2 必须在第二版重写的连接部位

- `App.jsx`、桌面侧栏、首页卡片和移动端导航入口。
- `src/auth/permissionCatalog.js`、部门/职位权限模板和服务端权限判断。
- 采购到货与仓库确认入库之间的业务接口。
- 出库、退回与项目材料成本之间的业务接口。
- Supabase 表、RLS、RPC、Edge Function、审计和存储桶权限。
- 第二版的加载状态、错误处理、登录失效和黑金视觉适配。

这些连接只在第二版文件上做最小增量修改，不复制旧分支对应公共文件。

### 3.3 绝对禁止迁移的内容

- 旧版登录、恢复账号、自定义会话和本地身份逻辑。
- 旧版 `baseRecordService`、云同步协调器、通用数据表映射等公共持久化实现。
- 旧版首页、应用外壳、人员管理、项目管理、采购管理、会计、考勤及其公共样式。
- 旧版 `.env`、Supabase 配置、测试数据和任何库存数据。
- 来源或用途不能明确证明属于仓库模块的共享代码。

默认规则是“来源不明即不迁移”。

## 4. 仓库业务范围

第二版新增一级“仓库管理”，包含：

- 仓库概览；
- 物品主档和多规格档案；
- 型号、尺寸、材质、单位、编码、最低库存；
- 多张物品照片；
- 系统二维码、厂家二维码、扫码和标签打印；
- 多仓库、项目现场仓、货架区和共享工具仓位；
- 当前库存和批次库存；
- 采购入库确认、出库确认、退回、调拨；
- 简洁的月度盘点；
- 不可删除的库存流水；
- 库存、出入库、调拨、盘点及缺货报表的筛选、打印、PDF 和 Excel 导出。

共享工具可记录存放位置和数量，但借用、归还流程继续属于现有“借工具/还工具”模块，不把两套业务混成一套。

## 5. 权威库存与成本规则

### 5.1 采购入库

采购到货只生成待确认记录，不立即增加库存。仓库负责人确认规格、验收数量、入库批次价格、仓库和货架后，服务端事务才增加批次库存并生成一次入库流水。允许分批到货和分次确认；相同确认请求重试不得重复入库。

### 5.2 出库

提交“我要出库”后状态为待仓库确认，不扣库存。仓库负责人选择实际批次和仓位并确认后，服务端按先进先出扣减。库存不足、仓位不完整或权限不足时整笔失败，不允许出现页面显示成功但库存未正确变化。

出库确认时把各批次实际成本快照到出库流水和项目材料成本。以后物品价格上涨或档案价格修改，历史出库成本不变。

### 5.3 退回

退回关联原出库记录。仓库验收并确认后，按原出库成本恢复库存批次或形成可追踪的退回批次，同时按原成本冲减对应项目材料成本。未确认不改变库存和成本。

### 5.4 调拨与盘点

调拨由一个服务端事务同时扣减来源仓位并增加目标仓位，总库存和批次成本不变。盘点按月、仓库和货架生成清单，使用者只录入实盘数和原因；仓库负责人确认后才生成盘盈、盘亏、损坏或报废调整流水。

### 5.5 审计原则

库存数量不允许由普通页面直接改写，只能由已确认业务产生不可删除流水。纠错通过反向冲销实现。关键操作保存单号、操作者、时间、物品规格、批次、仓位、数量、单价、金额、项目、来源单据和原因。

## 6. 第二版连接架构

### 6.1 身份与权限

沿用第二版 Supabase Auth、`employee_profiles`、部门/职位权限模板和 `SW-000` 固定规则。新增稳定权限键：查看仓库、维护档案、确认入库、确认出库/退回、调拨、盘点调整、查看成本、打印/导出。

“仓库管理部”可由管理员在部门模板中一次授予完整仓库权限；系统不恢复旧版个人权限或本地权限快照。浏览器隐藏无权入口只是体验层，RLS/RPC/Edge Function 必须再次验证当前 JWT、账号状态和实时权限。

### 6.2 采购、项目和会计

采购单仍是采购发生事实，仓库入库确认是库存事实，两者以稳定单据 ID 关联，不复制采购单。采购付款不增加库存，也不重复计入项目成本。

项目材料成本只来源于已确认出库的批次成本；退回按原成本冲减。项目、会计成本和老板驾驶舱通过同一只读模型消费仓库流水，避免仓库成本和手工成本重复计算。

### 6.3 数据库与照片

仓库数据使用规范化表、外键、唯一约束、数量检查、幂等键和不可变流水。数量与金额变化通过受权限保护的服务端事务 RPC 完成，浏览器不能直接组合多次写入模拟确认。

照片使用受控 Supabase Storage 路径和策略；数据库只保存受控对象引用和排序信息。系统二维码映射到稳定规格 ID，厂家二维码使用带唯一约束的外部码映射。

## 7. 界面设计

新增页面复用第二版黑金主题、桌面侧栏、首页业务卡片、按钮、表格、弹窗和移动端断点。仓库入口是新增一级模块，不改变现有模块顺序和业务含义。

“我要出库”升级为可搜索/扫码选择具体物品规格，显示照片、型号、尺寸、库存位置、可用数量、申请数量、项目和用途。申请阶段不向普通申请人暴露不必要的成本字段；仓库确认界面显示实际批次、仓位和成本摘要。

月度盘点优先简单：选择仓库和月份、生成清单、逐行录入实盘数、只看差异、填写原因、确认。打印和导出使用当前筛选结果。

## 8. 错误处理

- 所有关键确认均以服务端事务结果为准，网络失败不得显示成功。
- 幂等键防止双击、重试或断网恢复导致重复入库/扣库。
- 库存不足、非法数量、二维码重复、缺少项目/仓位或无权限返回明确中文错误。
- 前端不得在 RPC 失败时回退为本地扣库存。
- 登录失效或权限变化沿用第二版失败关闭规则，不恢复旧会话。
- 批量导出、图片加载或标签打印失败不影响已经确认的库存事务。

## 9. 隔离验证与发布边界

### 9.1 自动测试

- 仓库纯领域单元测试和旧仓库测试的第二版适配版本。
- 第二版导航、首页、权限目录和人员权限模板契约测试。
- 采购入库、FIFO 出库、历史成本冻结、退回冲减、调拨和盘点事务测试。
- 未授权、停用、首次改密、重复请求、并发库存不足和跨仓串库测试。
- 照片、二维码唯一性、报表筛选、打印和 Excel 导出测试。
- 全量第二版回归测试和生产构建。

### 9.2 本地数据库验收

使用隔离 Supabase，从空仓库数据开始，仅建立最少的测试员工和测试项目。模拟完整链路：建档 → 采购 → 仓库确认入库 → 多批次涨价 → 项目出库 → 退回 → 调拨 → 月度盘点 → 报表。确认历史成本不随新价格变化，并验证重复确认不会重复改变库存。

### 9.3 用户本地验收

启动独立端口的本地预览，明确标注“第二版 + 仓库移植测试”。用户确认页面风格、流程、数据和报表后，才另行制定线上备份、迁移、发布和回滚步骤。

本设计阶段和首轮开发阶段均不得部署 Vercel、不得执行线上数据库迁移、不得写入线上员工/项目/仓库数据。

## 10. 完成判定

只有同时满足以下条件，才可称为本地移植完成：

1. 仓库需求白名单全部可用；
2. 第二版原有自动测试和新增仓库测试全部通过；
3. 生产构建成功；
4. 旧版身份、会话、公共持久化和页面壳扫描为零；
5. 本地完整业务链路通过；
6. 用户完成本地预览确认；
7. 没有执行任何线上部署或线上数据库写入。
